# specs/ — 工作单元

每个要走定义段的 task = 一个文件夹（工作单元），从计划到测试全链路竖着放一起。
干某个增量时只加载它那一个文件夹，全上下文齐备，不用跨目录捞。

## 单元从哪来

需求入口在仓库根 `ISSUES.md`（issue 池）。池子里拆出的 task 若需要设计 / 定义，
就开一个 `specs/<版本或功能名>/` 单元；小修小补可不开单元直接开发（池子条目下留验收点即可）。

## 结构

```
specs/<版本或功能名>/
  README.md          单元导航 + 状态
  1-plan.md          拆解快照：池子条目回链 + task 一段话 + 验收点 + 范围边界
  2-design.md        设计：设计需求总结 + 实现契约（design-exploration 产出）
  3-prd.md           需求：用户故事 + 验收标准（prd-test-writer 产出）
  4-test-cases.md    测试：可执行测试用例（prd-test-writer 产出）
  _review/           视觉件（HTML 设计稿等），给人看
```

## 链路

`ISSUES.md 拆出 task → 1-plan → 2-design → 3-prd → 4-test-cases → 开发`（读 `4-test-cases` 写代码 + 测试跑绿）。
前一步是后一步的输入。缺步骤就没那个文件，正常。

## 角色边界

`.md` = 给 AI 的事实源；`_review/` 的 html = 给人看，**AI 默认不读**。

## 关于 2-design（重要）

新项目刚建出来没有任何设计规范文档，这是正常的。
2-design **不依赖任何全局设计系统**，只描述「本单元的设计需求 + 实现契约」。
当某种设计模式反复出现并稳定后，才考虑沉淀成 `docs/` 下的设计文档——
那是长出来的，不是一开始就要有的。

样板见 `_example-示例功能/`（教学示例，看懂后可整个删除）。
